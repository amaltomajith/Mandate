01 Overview

The one-paragraph version, if you read nothing else.

Mandate is an agentic spending firewall — a policy-enforcement layer between an AI agent and Razorpay. An agent asks Mandate for permission to move money. Mandate proves who is asking, checks whether that agent still holds a valid standing authorization, evaluates the merchant’s rules, and either lets the real Razorpay call through, escalates it to a human, or refuses it — then records exactly why, permanently.

Nothing is simulated at the edges: agents sign real requests with real Ed25519 keys, allowed actions are real Razorpay API calls, and every decision is a row in a real database the dashboard reads live.

The problem it exists for

Today an AI agent buying on a merchant’s behalf is invisible in the payment record — it uses a saved card as the human, or the merchant’s own API key. You cannot cap, rate-limit, or revoke a thing you cannot name. Mandate gives the agent a cryptographic name first; everything else follows from that.

04 Core concepts

Six nouns. Everything else is built from these.

Agent

A registered identity — an Ed25519 keypair — representing one piece of calling software. Accumulates its own trust score from its own record.

Policy rule

One of five types. All active rules are checked against every action, in a fixed priority order; the first match decides.

Mandate

A standing authorization for one agent to act for one customer. Revoking it blocks every future action under it, immediately.

Trace

A permanent record of one decision — what was asked, which rule governed it, what happened, and why, in plain language.

Escalation

What a step-up or trust rule produces instead of a refusal. It waits in a queue, and approving it is what actually executes the held action.

Trust score

0–100 per agent, from its own recent record. Not decoration: a rule reads it.

06 The five rule types

All active rules are checked against every action, in a fixed order. The first match decides, and its reasoning is what the merchant reads.

ordertypeRefuses or defers when…
1category_blockthe category is banned outright, at any amount
2capa per-transaction or per-day ceiling is exceeded
3velocitytoo many actions in a window — amount-blind, the pace is the signal
4trust_floorthe agent’s trust has fallen below a minimum, at any amount
5step_upthe amount is above a threshold — send it to a human

The ordering is a policy choice, not an accident. Hard bans and absolute ceilings come first because they are not judgment calls. trust_floor sits above step_up because “this agent has not earned the benefit of the doubt” is a stronger reason to involve a human than “this amount is large” — so a distrusted agent’s stated reason is its record, not an amount threshold that happened to also match.

07 Trust, and why it bites

A reputation signal nothing acts on is decoration. This one gates decisions.

Every agent starts at a neutral 50. The score moves with its own record: a clean approve-to-block ratio pushes it up, escalations nudge it down, and account age adds a small capped bonus so a brand-new agent cannot out-trust an established one on a lucky streak. A trust_floor rule reads that number — below the threshold, an agent’s actions are held for a human regardless of amount, because at that point the problem is the caller rather than the transaction.

Computed over recent decisions, not all history

An all-time score cannot be recovered from. An agent with hundreds of clean actions barely moves when it misbehaves, and one that misbehaved badly stays punished no matter how it behaves afterwards. Neither is what reputation should do — and a score that cannot move is one no gate can meaningfully act on.

A trap this design had to avoid

Once the floor starts holding an agent, every subsequent decision is an escalation — so if escalations are penalised heavily, the penalty becomes self-sustaining and the gate turns into a one-way trapdoor no amount of good behaviour reopens. Escalations are therefore weighted lightly, which puts a held agent’s equilibrium at 40 — above a floor of 35, so it recovers — while an agent genuinely being blocked settles near 29 and stays held. Changing either number has to preserve that ordering.

Forged requests count against nobody

Rejected signatures are recorded as traces and alerts, but never against an agent’s score. A request whose signature does not verify carries no proven identity — the signature is what proves it — so attributing it by the claimed agent id would let anyone destroy a competitor’s reputation by sending forgeries in their name.

09 Mapping a transaction to an agent

The agent never tells you who it is. It proves it, and the identity is derived from the proof.

  1. The agent builds a Signature-Input header carrying its agent id as keyid, and signs the method, path, authority, a digest of the body — and that header itself.
  2. The server looks up agents.public_key by that keyid, recomputes the body digest, and verifies the signature.
  3. The verified keyid is attached to the request and passed down as an argument.
  4. The trace is written with agent_id already set.

Because the keyid sits inside the signed material, you cannot lift a valid request and swap the keyid to impersonate another agent — the signature stops matching. And agentId is deliberately absent from the tool input schema, so it can never come from the request body. An agent can misdescribe an action’s category; it cannot misrepresent who it is.

Nothing here is hardcoded. An agent is a row carrying a public key: create one, point a signed client at the endpoint, and its transactions attach to it automatically — its own trust score, its own history, no code change. This deployment runs a single agent, so there is no onboarding screen; the mechanism is the signature, not a button.

10 The simulated agent

One agent, transacting continuously — not a scripted walkthrough.

Each tick picks a scenario by weight and then lets the real engine decide. A high-value action escalates because it genuinely crosses the step-up threshold, not because the simulation labelled it an escalation — so if a rule is retuned, the mix shifts with it. Purely random purchases would be an unbroken wall of “allow” and would never show the engine doing anything; the weighting is what makes every decision type surface on its own.

SpeedintervalEffect
Calm30scomfortably inside the velocity limit

That last row is the point of having a speed control at all: the guardrail can be watched working rather than only described.

12 What’s real vs. illustrative

Real

Every allowed action is a genuine Razorpay test-mode API call. Signature verification is real Ed25519 cryptography. Trust scores, traces, and mandate state are computed from actual history, not fixtures.

Labeled, not hidden

Only agents a merchant onboards are governed — there is no universal identity layer for arbitrary agents from the open internet yet, which is the gap this is built against. An action’s category is self-reported and unverified, so a hostile agent could misdeclare one to dodge a category rule; the action type cannot be faked. Signatures are verified then discarded, so a historical trace cannot be independently re-proved after the fact. Clerk runs on a development instance. subscription.create falls back to a clearly-flagged simplified mandate object when Razorpay Subscriptions is not activated on the account, and RazorpayX payouts were removed rather than stubbed because they need a registered business Razorpay itself gates.
